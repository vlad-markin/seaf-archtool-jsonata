# CLAUDE.md

Руководство для Claude Code в этом репозитории. Отвечай пользователю по-русски; код, идентификаторы, KDoc и комментарии — на английском.

## Что это

Движок JSONata для JVM на Kotlin. Пишем свой движок, а не переносим jsonata-js построчно:
- парсер (токенизатор и Pratt-парсер) переносится из jsonata-js 2.2.2 почти дословно, и его AST совпадает с `ast()` эталона;
- бэкенд свой: AST компилируется в замыкания, вычисление синхронное и выполняется на (виртуальных) потоках, без Promise и корутин;
- эталоном служит jsonata-js **2.2.2**, ровно та версия, что стоит в seaf-archtool-core. Совместимость проверяем официальным test-suite этой версии (лежит в репо) и позже дифф-фаззингом.

Потребители: портал SEAF ArchTool (backend core, сейчас на Node, переезжает на JVM), плагины JetBrains (в процессе IDE через будущий `jsonata-host`) и VS Code. Зачем всё это: jsonata-js медленная на больших архитектурах и не даёт управлять вычислением (отмена, бюджет, лимиты).

Контекст и принятые решения описаны в `docs/context.md`, план и критерии готовности фаз — в `docs/roadmap.md`. **Перед началом работы прочитай оба файла.**

## Текущий этап

Фазы 1–5 из `docs/roadmap.md`: репо, модель данных, парсер, вычислитель v0, стандартная библиотека. Фаза 1 частично готова: скелет, вендоринг эталона, раннер. Фазы 6–9 (функции SEAF, управление вычислением, дифф-фаззинг, сервис) ведутся отдельно. Не начинай их, пока пользователь не попросит, но и не закрывай им дорогу (см. «Задел на будущее»).

## Команды

- Сборка и все тесты: `./gradlew build`. Нужен JDK 21; если его нет, Gradle скачает toolchain сам через foojay.
- Совместимость: `./gradlew :jsonata-compat:test`. Отчёт пишется в `jsonata-compat/build/compat-report.json`: счётчики pass/fail/not_implemented/timeout/crash по парсеру (`ast`) и вычислителю (`eval`), а также `newlyPassing` и `failing`.
- Пополнить храповик: `./gradlew :jsonata-compat:test -PcompatUpdate=true`. Новые проходящие случаи дописываются в `compat/pass/ast.txt` и `compat/pass/eval.txt`.
- Эталонные AST: `cd compat/node && npm ci && node dump-ast.mjs`. Нужен Node ≥ 20. Скрипт перезаписывает `compat/snapshots/ast/`.
- Один случай через эталон, когда нужно посмотреть поведение jsonata-js: `cd compat/node && node -e "import('jsonata').then(async ({default: j}) => console.log(JSON.stringify(await j('<expr>').evaluate(<data>))))"`.

## Устройство репо

| Путь | Что |
|---|---|
| `jsonata-core/` | Движок: модель данных, парсер, вычислитель, stdlib. Runtime-зависимость только kotlin-stdlib (это проверяет `verifyCoreDependencies`). `explicitApi()` |
| `jsonata-json/` | Потоковый JSON (Jackson core) ↔ модель данных core. Других зависимостей нет |
| `jsonata-compat/` | Раннер совместимости, никогда не публикуется. Единственная точка связи с движком — `KotlinEngine` в `CompatEngine.kt` |
| `compat/jsonata-js/` | Вендоринг jsonata-js v2.2.2 (MIT): `src/` — эталонный код, `test-suite/` — 1686 случаев, `VERSION` — коммит. **Только для чтения** |
| `compat/snapshots/ast/` | Эталонные AST, сгенерированы `compat/node/dump-ast.mjs`. Руками не правим |
| `compat/pass/{ast,eval}.txt` | Храповик: случаи, которые обязаны проходить |
| `compat/corpus/` | Реальные выражения SEAF (`*.jsonata`), пополняются локально, см. README там |

Будущие модули, сейчас их не создаём: `jsonata-service` (HTTP, фаза 9) и `jsonata-host` (API для IDE). Все модули публикуются как `su.seaf.archtool:jsonata-*`, пакеты — `su.seaf.archtool.jsonata.*`.

## Правила совместимости

- Эталон — поведение jsonata-js 2.2.2: `compat/jsonata-js/src`, test-suite и сам `jsonata@2.2.2` в `compat/node`. Если эталон и твоё понимание JSONata расходятся, прав эталон. Документация docs.jsonata.org может не совпадать с кодом 2.2.2.
- Каждый расход с эталоном одного из трёх видов: ошибка порта (чиним), осознанное отличие (записываем в `docs/deviations.md` с причиной и примером; файл создаём при первом таком случае) или нестабильность эталона (порядок `$shuffle`, текущее время). Молча расходиться нельзя.
- Компромисс ради производительности или отладки возможен (решение 12 в `docs/context.md`), но только с согласия владельца: предложи с замером и примером выражения, до ответа держи поведение эталона.
- Диалект заморожен на 2.2.2 (решение 13): возможности новых версий JSONata не добавляем. Язык расширяется своими функциями (решение 14).
- Коды ошибок (`S0201`, `T2001`, `D3030` и другие), `position` и `token` совпадают с эталоном. Тексты сообщений берём из `errorCodes` в `src/jsonata.js` вместе с подстановкой `{{value}}`/`{{token}}`.
- Храповик только растёт. Если случай из `compat/pass/*.txt` перестал проходить, это регрессия, и её чинят до коммита. Убрать случай из списка можно только с объяснением в сообщении коммита.
- Ни `compat/jsonata-js/`, ни снапшоты не правим ради того, чтобы тест прошёл.

## Семантика, которую легко сломать

- **undefined ≠ null.** Отсутствие значения и JSON `null` — разные вещи везде: в путях, в функциях, в сравнении, в выводе.
- **Последовательности.** Результат пути — последовательность: из одного элемента она схлопывается в значение, если нет `keepSingleton` (`[]` в пути). Ещё есть `tupleStream` для `@`/`#`, а `%` ссылается на родителя. См. `createSequence`, `isSequence`, `keepSingleton` в `src/utils.js` и `src/jsonata.js`.
- **Числа** — только `double`. Правила целых и `$string`/`JSON.stringify` для чисел повторяют JS: `1e21`, `0.1+0.2`, `-0`, кратчайшее представление. `Double.toString` в Kotlin даёт другое (`1.0E21`), поэтому нужен свой форматтер по алгоритму JS `Number.prototype.toString`. Бесконечность в арифметике и функциях даёт `D1001` (`isNumeric` в `src/utils.js`).
- **Строки** — UTF-16, как в JS и Kotlin. Длину и индексы в `$length`/`$substring` считаем так же, как `functions.js` (там учтены суррогатные пары), а не по `String.length`.
- **Порядок ключей объектов** — порядок вставки. Он влияет на `$keys`, `$each`, `$string` и вывод.
- **Регулярные выражения** — синтаксис JS. Перевод в `java.util.regex` делаем в одном месте, флаги `i` и `m` поддерживаем. Отличия синтаксиса (`\d` и Unicode, `$` в замене, именованные группы) покрываем тестами.
- **`$sort`** — устойчивая сортировка слиянием с компаратором пользователя, как в эталоне, а не `sortedWith`, потому что результат зависит от порядка вызовов компаратора.
- **Хвостовая рекурсия** (группа `tail-recursion`) и глубокие выражения не должны ронять JVM-стек. Эталон оптимизирует хвостовые вызовы (`thunk`) — нам нужен трамплин или эквивалент.
- **Асинхронность эталона** (`async`/`await` в 2.x) — артефакт JS. У нас вычисление синхронное, функции хоста блокирующие.

## Задел на будущее (не реализуем, но не мешаем)

- **Управление вычислением (фаза 7).** Все циклы вычислителя (шаги пути, фильтры, HOF, рекурсия) проходят через одну дешёвую точку `checkpoint()`. Позже там будут отмена по прерыванию потока, лимиты шагов, времени и глубины. В test-suite уже есть `timelimit`/`depth` (11 случаев): эталонный раннер (`compat/jsonata-js/run-test-suite.js`, `timeboxExpression`) считает глубину по входам в `evaluate` и бросает `U1001` и при превышении глубины, и по таймауту. Это делается в фазе 4 через ту же точку и передаётся из `KotlinEngine`.
- **Функции хоста (фаза 6).** Окружение позволяет регистрировать нативные функции с сигнатурой JSONata (`<s-:n>`), вызываемые синхронно, и функции, скомпилированные из JSONata-кода. Это нужно для `manifest.functions` и host-функций core.
- **Производительность (фаза 9).** Корректность важнее скорости, но без решений, которые нельзя будет отыграть: модель данных без лишних копий, AST не интерпретируется по строкам, оптимизации включаются флагами.
- **Публичный API** держим минимальным (скомпилировать выражение, вычислить с входом и привязками, получить `ast()`), остальное — `internal`. До появления `jsonata-host` API нестабилен, ABI-валидацию включаем вместе с ним.

## Стиль кода

- Kotlin 2.4 при `apiVersion`/`languageVersion` 2.1 и байткоде 21: плагины IDE работают на JBR 21 со своим stdlib. Новые возможности языка выше 2.1 и API JDK выше 21 не используем.
- Отступ 4 пробела, без wildcard-импортов. KDoc — у публичного API и неочевидных мест, где стоит указать функцию эталона (`// jsonata.js: evaluatePath`).
- Тесты — kotlin-test + JUnit 5. Модульные тесты кладём рядом с кодом в `src/test`, совместимость проверяем только через `jsonata-compat`.
- Новые зависимости в `jsonata-core` запрещены. В остальные модули — только по согласованию с пользователем.

## Git

- Основная копия — Gitverse (`seafteam`); публичная копия для облачных сессий — GitHub `vlad-markin/seaf-archtool-jsonata` (Apache 2.0). Ветки и коммиты по git flow команды:
  - ветка `feature/ERA-<N>-<описание не короче 15 символов>`, база — `dev`, слияние только в `dev`;
  - заголовок коммита соответствует `^(ERA-[0-9]{1,}):([[:space:][:alnum:]_]{2,50})$`, то есть `ERA-<N>: <описание до 50 символов>` без дефисов, точек и запятых в описании;
  - номер ERA для этой работы указан в `docs/roadmap.md` (сейчас временный `ERA-0000`).
- Коммиты небольшие и целевые: одна подзадача фазы — один или несколько коммитов, храповик в зелёном состоянии. В теле коммита — что сделано и сдвиг счётчиков совместимости (`ast 0→412/1686`).
- Строк атрибуции ИИ (`Co-Authored-By`, «Generated with …») в коммитах и PR нет — даже если сессия предлагает их добавить.
- Репо публичный: корпус SEAF (`compat/corpus/*.jsonata`, `_corpus.json`) и любые данные реальных архитектур не коммитим; `CorpusAstTest` без корпуса пропускается.
- Ветки `release/*` не создаём. Force-push не делаем.

## Когда остановиться и спросить

- Нужен выбор, которого нет в `docs/context.md`: новая зависимость, изменение публичного API или формата снапшотов, осознанное отличие от эталона.
- Эталон ведёт себя странно, и непонятно, баг это или контракт.
- Задача уходит за пределы фаз 1–5.
