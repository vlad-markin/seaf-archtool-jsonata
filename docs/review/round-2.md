# Ревью круга 2: задание на исправление

Ревью коммитов `5bd621a..eefcd71` двумя независимыми моделями, замечания сведены и перепроверены прогонами против `jsonata@2.2.2` (Node 22). Все RV-1…RV-16 круга 1 закрыты по существу; ниже — регрессии и недозакрытия. Исправлять **до** продолжения `docs/plan/cloud-task.md` (сразу после текущего шага), по порядку: major → minor. Каждое исправление — с регрессионным тестом; храповик, `debugDiffs` и фаззинг зелёные. Отметки — в `docs/progress.md`.

## Решения владельца

- **Токен ошибки встроенной функции, вызванной через HOF или `~>`:** верно имя функции (как сейчас в движке). Эталон в свежем процессе даёт `null`, а на общем объекте функции — имя из прошлого вызова. Записать отличием в `docs/deviations.md` (следующий свободный номер) и учесть в классификаторе фаззинга как одно узкое правило.
- **Формат внешних случаев для replay:** JSONL, строка `{expr, data, bindings?}`; режим каталога не нужен. `bindings` обязаны доходить до обоих движков.


Сборка: `./gradlew build` остаётся зелёной; счётчики храповика (ast 1686/1686, eval 1686/1686) и ловушек не падают. Эталон — `jsonata@2.2.2`, Node 22. Пути — от корня репозитория движка. Кучу в проверках памяти ограничивать (`-Xmx1g`, как `tasks.test`).

### RV2-1 [major] `lastCalls` удерживает все вызванные лямбды

- Где: `engine/Runtime.kt:105-111` (`IdentityHashMap<Lambda, CallSite>` на `EvalContext`).
- Суть: исправление RV-9 перенесло «последнее место вызова» с лямбды в контекст вычисления; ключи сильные, поэтому каждая лямбда, вызванная по имени, вместе с кадром замыкания живёт до конца вычисления. Раньше `lastSite` был полем лямбды и уходил в GC вместе с ней. Шаблон «локальная функция в блоке внутри `$map`» обычен в выражениях SEAF.
- Воспроизведение (`-Xmx1g`), вход отсутствует: `$sum($map([1..20000], function($v){ ($t := [1..20000]; $f := function($x){ $x + $count($t) }; $f($v)) }))`. Ожидание (так на `5bd621a`): `600010000`; сейчас `OutOfMemoryError: Java heap space`. Замер остатка кучи на `$count($map([1..N], function($v){ ($f := function($x){$x}; $f($v)) }))`: N = 300 000 → 95 МБ, N = 1 000 000 → 305 МБ (база — 5 МБ при любом N). Проверено: замена на `WeakHashMap` убирает OOM (по отчёту A; мой прогон подтвердил OOM и результат базы).
- Исправление: слабые ключи (проверить `equals/hashCode` у `Lambda` — должны быть идентичными) либо хранить место вызова в кадре вызова и переносить в ошибку при раскрутке (согласовать с P-01: тот же код `applyInner`). Тест на удержание памяти: N = 1e6 при ограниченной куче.

### RV2-2 [major] `RegexFunction` как значение — разделяемое изменяемое состояние

- Где: `engine/Regex.kt:372-386` (`lastIndex`, `lastSubject`, `matcher`; `CheckedChars` создаётся с `EvalContext` того вычисления, где `Matcher` построен), `Regex.kt:457` (`nextMatch`).
- Суть: regex, вышедший из вычисления (результат, привязка, функции манифеста), несёт `Matcher` с контекстом создателя. Следствия, все воспроизведены: (а) чужой дедлайн — `D1012` в вычислении без лимита; (б) собственный дедлайн обходится — `Matcher` без `CheckedChars` переиспользуется, если строка (по идентичности) та же; (в) параллельные вычисления делят `Matcher`: неверные результаты и `StringIndexOutOfBoundsException` из публичного API (CAP-9(5)). Противоречит записи RV-9 в `docs/context.md` («функцию можно безопасно вызывать из нескольких вычислений одновременно»).
- Воспроизведение 1. `r` = результат `Jsonata.compile("/b/").evaluate(null)`; `s` = `"a"×20000 + "b"` (один объект `StringValue`). Вычисление `$contains($, $r)` с входом `s`, привязкой `r`, `timeoutMillis = 50` → `true`; через 150 мс то же вычисление без лимитов → ожидание `true`, сейчас `D1012 «Evaluation timeout after 50 milliseconds»`; `$match($, $r).index` → ожидание `20000`, сейчас `D1012` (на `5bd621a` — `true` / `20000`).
- Воспроизведение 2. `r` = результат `Jsonata.compile("/(?:a*)*?b\\0/").evaluate(null)`, `s` = `"a"×26 + "!"` (один объект). `$contains($, $r)` без лимитов (≈1,9 с, `false`), затем то же с `s`, `r` и `timeoutMillis = 50` → ожидание `D1012` через ~50 мс; сейчас `false` через ~1,9 с. Контроль — свежий `r` и свежая строка: `D1012` за 50 мс.
- Воспроизведение 3. `r` = `/b+/` как выше; 8 потоков × 4000 вычислений `$match($, $r).index` на разных строках вида `"a"×k + "b" + "a"×j + "bb"`. Ожидание: совпадает с `$match($, /b+/).index` в каждом вычислении (общий `lastIndex` есть и в эталоне при разделении объекта, но исключений быть не должно). Сейчас: ~5300 из 32 000 расходятся, в двух вычислениях `StringIndexOutOfBoundsException`.
- Исправление: `Matcher` и `lastIndex` — на вызов функции (или в `EvalContext` по идентичности `RegexFunction`, как `lastCalls`), `CheckedChars` привязывать к текущему вычислению; не кэшировать `Matcher` в самой функции. Тесты: regex-значение в двух вычислениях подряд (с таймаутом и без, в обе стороны) и параллельно, с проверкой отсутствия исключений JVM.

### RV2-3 [major] `ObjectValue.remove` квадратичен, цикл удаления без контрольной точки

- Где: `value/Value.kt:249-262` (`System.arraycopy` двух массивов + полная пересборка `HashMap`-индекса при >8 ключей на каждое удаление), `engine/Evaluator.kt:187-197` (циклы обновления и удаления трансформации без `ctx.tick()`).
- Воспроизведение: `$count($keys($ ~> |$|{}, $keys($)|))`, вход — объект из N ключей `k0…k{N-1}` (значения числа). N = 2000 → ~40–120 мс, N = 10 000 → ~0,3–0,7 с, N = 30 000 → 3–5 с; на `5bd621a` — 3 / 5 / 11 мс, эталон при N = 30 000 — ~21 мс. Результат `0` у всех. С `timeoutMillis = 100` и N = 30 000: результат `0` через ~3 с, `D1012` нет (ожидание: `D1012` в пределах малого запаса).
- Суть: компактное хранение (749ac8b) добавило квадратичность — то, что план P-04 должен снимать; RV-6 («копирование при трансформации») закрыт не полностью.
- Исправление: при удалении не пересобирать индекс (помечать слот удалённым и уплотнять лениво либо удалять ключ из индекса и сдвигать индексы только при уплотнении); `ctx.tick()` в циклах `update`/`delete` трансформации. Случай — в `compat/bench`; тест с коротким таймаутом.

### RV2-4 [major] Классификатор фаззинга скрывает расхождения

- Где: `compat/fuzz/DiffFuzz.kt:145-151` (категория `error-position-token`: любая разница позиции при равном токене объявляется «нестабильностью эталона»; вторая ветка — любая разница токена для функции, переданной значением), `DiffFuzz.kt:190-191` (`KnownDifferences.explain`: «DEV-09» для любых двух разных кодов, если в тексте есть `[`/`{`, а до закрывающей скобки — запятая; регулярное выражение `[\[{][^\]}]*,` совпадает, например, с `$f([1,2])` и `{"a":1,"b":x}`).
- Суть: гейт фазы 8 «0 расхождений вне DEV» (TC-06) на replay реальных выражений (почти все содержат `{…,…}`) перестаёт видеть регрессии кодов и позиций ошибок, включая P-01 (позиция ошибки из тела лямбды). В кампании seed 3 (30 000 случаев) правило «позиция» объяснило 54 расхождения, DEV-09 — 0; сейчас вреда не нанесено, но гейт неточен.
- Ожидание: объяснение расхождения ставится только при подтверждающем признаке; тест классификатора, где разные коды и позиции остаются необъяснёнными.
- Исправление: DEV-09 — только если повторное вычисление значений конструктора по одному даёт именно эти два кода (или в конструкторе ≥2 значений с ошибками); «позиция» — только если в свежем процессе эталона позиция совпадает с движком либо выражение передаёт встроенную функцию значением (`~>`, HOF); добавить в отчёт отдельный счётчик «объяснено позицией» с выборкой для просмотра.

### RV2-5 [major] Replay отбрасывает привязки, сайдкар не защищён от зависания

- Где: `compat/fuzz/DiffFuzz.kt:207-210` (`readCases` читает только `id/zone/expr/input`), `DiffFuzz.kt:50-58` (`Sidecar.evaluate` не отправляет `bindings`), `compat/node/sidecar.mjs:17` (`{ timeout: 5000 }` — такой опции в `jsonata(expr, options)` у 2.2.2 нет), `DiffFuzz.kt:63` (`readLine` без таймаута).
- Суть: протокол сайдкара принимает `bindings`, но строка replay `{"id":"b1","expr":"$x + 1","bindings":{"x":1}}` считается без привязки на обеих сторонах и «совпадает» (`undefined` с обеих сторон) — ложный зелёный. Выражения корпуса SEAF рассчитывают на `$self/$params`. Зависший случай эталона (бесконечная рекурсия/цикл в jsonata-js) блокирует прогон навсегда.
- Воспроизведение: `:jsonata-compat:fuzz -Pcases=<файл>` со строкой выше. Ожидание: либо привязка передана обеим сторонам (`$x + 1` → `2` у обеих), либо прогон останавливается с ошибкой о неподдерживаемом поле `bindings` — но не тихое совпадение.
- Исправление: читать `bindings` в `readCases`, передавать в сайдкар и в вычисление движка; неизвестные поля строки — ошибка; таймаут на случай на стороне сайдкара (`Promise.race`) или чтение с таймаутом в Kotlin (случай — категория «эталон завис», не падение прогона); убрать мнимую опцию `timeout`.

### RV2-6 [minor] `tick()` в нативных циклах стандартной библиотеки

- Где: `engine/StandardLibrary.kt:129` (`sum`), `137` (`extreme`), `148` (`average`), `53` (`join`); функции не получают `EvalContext`.
- Суть: после входа в функцию до возврата дедлайн не проверяется. Масштаб: предсозданный массив из 20 млн единиц, `$sum($)` с `timeoutMillis = 1` вернул результат за ~74 мс (`$max` — ~38 мс); `$count($map($, function($v){$v}))` на том же входе даёт `D1012` за ~1 мс. Цикл линеен и быстр, поэтому уровень minor (B дал major); критерий RV-6 «точка во всех циклах» не выполнен.
- Исправление: передать контекст и вызывать `tick()` в циклах; регрессионный тест на предсозданном большом массиве (вход через API, не диапазоном).

### RV2-8 [minor] Нестабильность эталона «позиция и токен» не записана

- Где: `docs/deviations.md:164-167`, `engine/Evaluator.kt:80-89`.

### RV2-9 [minor] DEV-09 не охватывает общую regex-переменную в конструкторе

### RV2-11 [minor] Контракт потока вызова нативной функции

### RV2-14 [minor] `\k<имя>` внутри класса символов принимается

- Где: `engine/Regex.kt` (транслятор), `docs/deviations.md` DEV-04.
- Воспроизведение: литерал `/(?<x>a)[\k<x>]/` (вычисление выражения-литерала без входа). Эталон: `SyntaxError: Invalid regular expression … Invalid escape` (в sidecar — `crash`). Движок: принимает, результат — функция. DEV-04 обещает `X0003` на синтаксис, недопустимый в JS. Базу не проверял (возможно, не регрессия).
- Исправление: транслятор отвергает `\k<…>` внутри `[...]` при наличии именованных групп (`X0003`) либо запись в DEV-04 с причиной; случай — в ловушки.
