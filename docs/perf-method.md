# Методика замеров производительности и памяти

Стенд истории 6 (CAP-14): синтетика 10/50/200 тыс. компонентов, 15 запросов, движок против jsonata-js 2.2.2. Тот же стенд меряет цену отладки (CAP-12) и сравнивает версии движка (A/B). Числа из облака — ориентир: машина общая и шумная. Числа для приёмки снимаются локально на выделенной машине и пишутся в `docs/reports/perf-<дата>.md` (шаг 6.4).

## Состав

| Что | Где |
|---|---|
| Генератор модели `systems → containers → components` (теги, свойства, связи; 1 система = 5 контейнеров × 20 компонентов) | `jsonata-bench/.../Generator.kt`, побайтно как `gen.js` оценки порта dashjoin (mulberry32, seed 42) |
| Запросы: `path_filter`, `path_tags`, `group_agg`, `group_nested`, `join_scan`, `join_index`, `sort_fn`, `orderby`, `map_filter_reduce`, `strings`, `regex`, `recursion_tree`, `tail_loop`, `fib` и `deep_map` (случай обрыва сегментированного стека, условие У1) | `jsonata-bench/queries/*.jsonata`, размеры и пометки — `queries/index.json` |
| Раннер движка | `jsonata-bench/.../StandRunner.kt` |
| Раннер jsonata-js 2.2.2 | `compat/node/stand.mjs` (пакет `jsonata@2.2.2` из `compat/node`) |
| Оркестратор: данные, оба движка, сравнение, сводка, бисекция кучи | `jsonata-bench/.../Stand.kt`, задача `:jsonata-bench:stand` |
| A/B двух ревизий движка | `scripts/stand-ab.sh` |

## Запуск

```bash
cd compat/node && npm ci && cd ../..                          # jsonata@2.2.2, Node 22
./gradlew :jsonata-bench:stand                                # 10/50/200 тыс., все запросы, оба движка
./gradlew :jsonata-bench:stand -Psizes=10000 -Pqueries=sort_fn,orderby -Pengines=jvm,js
./gradlew :jsonata-bench:stand -Psizes=200000 -Pheap=true     # + минимальная куча (бисекция)
scripts/stand-ab.sh <rev A> <rev B> 10000 5                   # A/B, 5 раундов вперемешку
scripts/stand-ab.sh <rev A> <rev B> 10000 5 "" listener       # цена слушателя без точек (CAP-12)
```

Результаты: `jsonata-bench/build/stand/summary.md` (таблица), `results.jsonl` (все записи обоих движков), `results/<запрос>-<размер>.{jvm,js}.json` (результаты первой итерации). Данные и результаты в git не хранятся.

## Как меряется время

- Один процесс на пару «движок × размер»; все запросы подряд в одном процессе. Данные читаются один раз, разбор JSON в замер не входит.
- Компиляция — медиана 200 компиляций, отдельно от вычисления.
- Прогрев: 10/5/3 итераций для 10/50/200 тыс., но не дольше 15 с; затем 20/10/5 измеряемых итераций, не меньше 3 и не дольше 20 с суммарно (`-Pwarmup`, `-Piters` меняют числа).
- Перед каждой итерацией — принудительная сборка мусора (`System.gc()` / `global.gc()`), вне замера.
- В записи: медиана, p95, минимум, максимум, все времена, load average (1 мин) — по нему видно, была ли машина занята.
- JVM: `-Xms3g -Xmx3g -XX:+UseG1GC -Xss16m` (`-Pxmx`), сборщик пишется в сводку. Node: `--expose-gc --stack-size=65500 --max-old-space-size` той же величины.
- jsonata-js на `sort_fn`/`orderby` от 50 тыс. и `recursion_tree` на 200 тыс. не запускается: сортировка слиянием 2.2.2 квадратична по времени и памяти и падает по памяти (`js_sizes` в `index.json`); в сводке пара помечена «не запускался».

## Сравнение результатов

Результат первой итерации каждого запроса обоих движков сравнивается как значение (`=` JSONata: глубокое равенство, порядок ключей не важен) и как текст. «Равны (порядок ключей другой)» — сигнал проверить ORD-правило; «различаются» — ошибка порта или отличие из `docs/deviations.md`, разбирается до приёмки.

## Память

- **Аллокации на вычисление** (JVM): `com.sun.management.ThreadMXBean.getTotalThreadAllocatedBytes()` до и после, по всем потокам — глубокие вычисления идут на потоках сегментов стека. Node даёт только нижнюю оценку: `heapUsed` после минус до.
- **Пик кучи во время запроса.** JVM: сумма пиков heap-пулов (`MemoryPoolMXBean.resetPeakUsage/getPeakUsage`) за итерации, включая данные. Node: `v8.getHeapStatistics().used_heap_size` в конце итерации — вычисление jsonata-js не отдаёт управление таймерам, поэтому выборки по ходу нет; это нижняя оценка.
- **Минимальная куча, при которой запрос проходит** (главная метрика CAP-14 п. 5, `-Pheap=true`): бисекция `-Xmx` и `--max-old-space-size` до 5 % (не точнее 4 МБ); на каждом шаге — отдельный процесс, одно вычисление (`--once`). Оба движка в бисекции читают модель **из строки**: в Node потокового разбора нет, `JSON.parse` держит текст (70 МБ на 200 тыс.) рядом с деревом, поэтому и JVM разбирает из строки (ревью RV3-21). Отдельная строка «(только разбор)» — минимум одного разбора (`--once=@parse`); у запроса, чей минимум равен ему с точностью бисекции, ячейка помечена «= разбор»: этот минимум задаёт разбор, а не запрос, и сравнивать по нему движки нельзя. Минимальная куча JVM зависит от сборщика — он фиксирован (G1) и пишется в сводку. Числа до RV3-21 (JVM читала поток, V8 — строку) несравнимы.

## A/B версий движка

`scripts/stand-ab.sh A B [размер] [раунды] [запросы] [режим]` собирает `jsonata-core` и `jsonata-json` каждой ревизии в git worktree (`jsonata-bench/build/ab/`) и гоняет текущий `StandRunner` с ними поочерёдно: каждый раунд — A и B по разу, порядок чередуется. В таблице — медиана медиан раундов, Δ и разброс раундов. Решение «быстрее/медленнее» принимается, только если Δ больше разброса. Режимы: `plain`, `listener` (слушатель без точек останова — так подключается IDE), `profiler` (оба — с истории 5).

## Угрозы достоверности

- Облако: общая машина, load average до 1–2, разброс медиан между прогонами до 2× на коротких запросах. Для приёмки — выделенная машина, `nice -n -10` или изолированные ядра, повторы.
- JMH не используется: нужен одинаковый способ мерить JVM и Node.
- `System.gc()` перед итерацией уменьшает влияние сборок на соседние итерации, но не убирает сборки внутри итерации; их число на Node пишется (`gc_during_eval_total`).
