# Контекст и решения

Выжимка того, что решено вне этого репо (спека `add-jsonata-cache-driver-contract` в seaf-archtool-specs, ADR `seafteam.adr.jsonata_cache_driver` в модели архитектуры). Облачной сессии этих репо не видно, поэтому здесь — всё, что нужно для фаз 1–5 и чтобы не закрыть дорогу фазам 6–9.

## Почему свой движок

jsonata-js на больших архитектурах медленная (сотни тысяч объектов в манифесте) и не отдаёт управление: вычисление нельзя отменить, ограничить по времени или шагам, нельзя посчитать его стоимость. Существующий порт dashjoin/jsonata-java — построчный перенос JS, его проблемы те же. Его можно смотреть как подсказку для сложных мест (даты, `$formatNumber`, регулярные выражения), но код не копируем: архитектура другая.

В октябре 2026 форк dashjoin оценили всерьёз (публичный репо `vlad-markin/jsonata-java`, ветка `claude/eval-js-2.2.2`, отчёт `compat-eval/REPORT.md`): каталог из 50 расхождений с jsonata-js 2.2.2 и их причины, результаты дифф-фаззинга, прототип отладочного API (ветка `claude/debug-api`). Этот отчёт — готовый список ловушек для нашего движка, читай его перед фазами 4–5. Владелец выбрал свой движок на Kotlin, а не развитие форка (2026-10-25).

## Принятые решения

| # | Решение | Следствие для фаз 1–5 |
|---|---|---|
| 1 | Парсер — перенос jsonata-js 2.2.2, AST совместим с `ast()` | Фаза 3 сверяется со снапшотами AST |
| 2 | Бэкенд свой: IR/AST → замыкания, ленивые последовательности и оптимизации — позже, под флагами | Фаза 4 пишет простой компилятор в замыкания, не интерпретатор по строкам |
| 3 | Только JVM. Вместо асинхронности — синхронное вычисление на виртуальных потоках, блокирующие вызовы функций хоста | Никаких Promise/Future/корутин в вычислителе |
| 4 | Отмена и бюджет — прерывание потока + контрольные точки | Одна точка `checkpoint()` во всех циклах (фаза 4) |
| 5 | Модель данных JSON — своя компактная, чтение потоковое (Jackson core) | Фаза 2; `jsonata-core` без Jackson |
| 6 | Пользовательские функции из манифеста (`functions`: `code` на JSONata, `params`/`result` в JSON Schema, параметры-лямбды) нужны | Механизм регистрации функций в фазе 4 должен поддерживать функции, скомпилированные из JSONata |
| 7 | Host-функции core считаются в Kotlin; колбэк к хосту — только загрузка ресурсов внутри `parsesource` | Нативные функции — синхронные, с сигнатурой JSONata |
| 8 | API сервиса: сессии/документы по id (основной) + разовый «документ + выражение» | Фаза 9; на ядро влияет только одно: разобранный документ переиспользуется между выражениями, поэтому вычисление не мутирует входные данные |
| 9 | Движок получает озеро и датасеты только через драйвер кэша (интерфейс в `jsonata-core`), сам в кэш core не пишет | Фаза 6+; в фазах 1–5 не нужно |
| 10 | Для IDE — модуль `jsonata-host` (по образцу `smartants-host`): узкий API, потоки и отмена у хоста, байткод 21, только kotlin-stdlib | Ядро без зависимостей и без API JDK > 21 |
| 11 | Артефакты `su.seaf.archtool:jsonata-*` в Maven Central | Пакеты `su.seaf.archtool.jsonata.*` |
| 12 | Совместимость с 2.2.2 максимальная, но не любой ценой: где отличие даёт заметный выигрыш в производительности или в отладке, владелец готов на компромисс | Такие отличия не делаем молча: предлагаем владельцу с замером и примером, после согласия — запись в `docs/deviations.md` |
| 13 | Диалект заморожен на jsonata-js 2.2.2: новые версии JSONata не догоняем | Не тащим возможности из master/3.x; эталон и test-suite остаются 2.2.2 |
| 14 | Свои функции для архитекторов — главный путь развития языка: нативные (Kotlin) и на JSONata (`manifest.functions`), со своей сигнатурой, документацией и ошибками | Реестр функций в фазе 4 проектируем как публичное расширение, а не внутреннюю таблицу stdlib; имена stdlib не переопределяются без явного флага |
| 15 | Отладка — требование первого класса: позиции в исходнике у каждого узла, стек вызовов JSONata, точки останова, пошаговое выполнение, значения переменных фрейма; позже DAP в языковом сервере | Компилятор в замыкания сохраняет позицию узла и даёт хук «вход/выход узла» с нулевой ценой, когда отладчик выключен (флаг на этапе компиляции) |
| 16 | Лицензия репо — Apache 2.0 (`LICENSE`, `NOTICE`); репо публичный на GitHub для облачных сессий, основная копия — Gitverse | Ничего закрытого в репо: корпус SEAF и снапшот корпуса в `.gitignore` |
| 17 | Режим совместимости — одна настройка движка: по умолчанию поведение jsonata-js 2.2.2 (включая его ошибки), согласованные отличия действуют только при включённом флаге. В инструменте флаг инсталляции переключает всё целиком на JVM-движок, jsonata-js тогда не используется нигде | Каждое согласованное отличие и исправление ошибки эталона реализуется за этой настройкой, а не вместо поведения эталона; test-suite 2.2.2 гоняется в режиме по умолчанию |
| 18 | Реестр функций: регистрация имени, уже занятого функцией stdlib (или другой зарегистрированной), — ошибка, без тихой подмены. Коды собственных ошибок движка (лимиты, отмена, реестр, расширения) — в формате кодов 2.2.2 со своей буквой: `X0001`… | Коды эталона (`S`, `T`, `D`, `U`) не занимаем своими; новые коды и тексты — в одной таблице рядом с `errorCodes` |

## Открытые вопросы (не блокируют фазы 1–5)

- Размещение движка после переезда backend core на JVM: в процессе backend или отдельный сервис в k8s. Решение — после замеров на больших архитектурах.
- Нужен ли движку свой кэш (вычисленные датасеты, результаты выражений).
- Состав и API отладчика, механизм регистрации своих функций, политика компромиссов — готовится спека (ERA-0000-jsonata-kotlin). До неё действуют решения 12–15 в общем виде.
